# 0012 — Cross-device sync

**Status:** `Draft`
**Depends on:** 0003, 0007, 0008
**Amends**: 0001 G7, 0002 C2, 0011

Dropbox is the first provider. The design MUST NOT bake Dropbox's API shape into
the rest of the app, because a second provider is planned and retrofitting an
abstraction later is expensive.

## Model

**SY1** — The architecture is **local-first**. IndexedDB is the source of truth.
The remote copy is a convenience and a backup, never a prerequisite.

**SY2** — No user action MUST be blocked on the network. Every sync operation
MUST be fire-and-forget from the user's perspective: the UI stays responsive and
the entry is already saved locally before any push is attempted.

**SY3** — A failed or impossible sync MUST NOT cause data loss, and MUST NOT
block, disable or degrade any feature. Offline is a normal state.

**SY4** — The remote file MUST reuse the JSON backup envelope from 0008 exactly.
One format, two consumers: the app's import path and the sync engine. A separate
sync format would be a second schema to maintain and would drift.

**SY5** — Sync and backup are separate concerns and both MUST exist. The remote
file is a single blob in one provider account: deleting it, losing the account, or
corrupting it is one mistake away from total loss. The local export (0007) remains
the durable guarantee.

## Provider abstraction

**SY6** — Sync logic MUST depend on this interface, not on a Dropbox client. The
interface lives in `sync/provider.ts`; the Dropbox implementation lives in
`sync/dropbox/`.

```ts
interface SyncProvider {
  readonly id: string
  /** Restore or acquire credentials. Must be safe to call when already valid. */
  ensureAuth(): Promise<void>
  /** Discard credentials. Local data MUST be untouched. */
  signOut(): Promise<void>
  /** Current state, for the settings UI. */
  status(): Promise<{ authenticated: boolean; account: string | null }>
  /**
   * Fetch the remote blob. MUST return `null` for "does not exist", which is
   * distinct from an error. MUST return the provider revision so callers can
   * detect concurrent modification.
   */
  pull(path: string): Promise<{ body: string; rev: string } | null>
  /**
   * Write the blob. `expectedRev` MUST be enforced by the provider so a
   * concurrent write is rejected rather than clobbered. Returns the new rev.
   */
  push(path: string, body: string, expectedRev: string | null): Promise<{ rev: string }>
}
```

**SY7** — The interface MUST NOT leak provider concepts. No `dropboxPath`, no
`rev` in shared code beyond the opaque `expectedRev` string, no Dropbox-specific
error types above this boundary.

**SY8** — Provider errors MUST be normalised into a small shared set — `Auth`,
`RateLimited`, `NotFound`, `Conflict`, `Network`, `Unknown` — each carrying
whether it is retryable. The engine MUST NOT branch on provider error shapes.

**SY9** — OAuth specifics (endpoints, scopes, token refresh, device flow) MUST
stay inside the provider module. Adding a provider MUST NOT require touching the
engine.

**SY10** — Provider API details referenced by this spec MUST be verified against
current vendor documentation during implementation rather than taken from this
document. Specifically: OAuth PKCE support, the exact scope strings, app-folder
path semantics, the revision/conflict-detection field, and token refresh
behaviour. This spec deliberately does not assert them.

## Authentication

**AU1** — Dropbox is specified as an OAuth provider, not a stored-password one.
OAuth avoids the app handling the user's Dropbox password, and PKCE means no
client secret is required, which keeps the app compatible with 0009 C3 (no
secrets in the build).

**AU2** — The app MUST use the authorization-code flow with PKCE. An implicit
flow MUST NOT be used.

**AU3** — The OAuth client id is public and MAY be embedded in the bundle. This
is expected and safe under PKCE. The app MUST NOT be misleading about this or
pretend the id is a secret.

**AU3.1** — The client id MUST be resolvable at runtime, not only from a build-time
variable, so a user can supply their own without a rebuild and redeploy
(`SPECS/todo.md` item 6). Precedence: a value stored by the user wins over a
build-time default, so an already-configured deployment is unaffected. The stored
copy lives in `localStorage` because the redirect handler reads it synchronously
before the app renders (0011 R5).

**AU3.2** — Changing the client id MUST invalidate the cached provider. Otherwise
the new instance carries the previous id and OAuth fails confusingly against a
stale client.

**AU4** — Redirect handling MUST work from a GitHub Pages origin, which means the
redirect URI is known and fixed at build time.

**AU4.1** — The PKCE verifier and `state` MUST be persisted before the redirect and
read back afterwards. The OAuth round trip is a full page navigation, so a verifier
held only in memory is gone by the time the code returns, redemption fails, and the
user is told they are not connected after an authorisation that appeared to
succeed. This is the whole point of PKCE: the verifier is what binds the token
request to the authorisation request, and those are necessarily two page loads.

**AU4.2** — The stored verifier MUST be scoped to `sessionStorage`, not
`localStorage`: it needs to survive a same-tab navigation and nothing more, and
`localStorage` would leave a token-exchange credential lying around indefinitely
(0011 R7).

**AU4.3** — The verifier MUST be single-use. Clear it once redeemed, and expire it
after a short window, so a code cannot be replayed.

**AU4.4** — Nothing may depend on the callback having completed before the app
renders. The redirect handler MUST be started without being awaited, so a slow or
unreachable Dropbox never delays startup (0002 O-1). Anything that needs to know the
outcome — the Sync panel deciding between connected and not connected — MUST await
the same promise rather than racing it. Querying the token store before the exchange
finishes reports "not connected" for an authorisation that worked.

**AU9** — `state` MUST be verified against the value stored when the authorisation
began, and a mismatch MUST be rejected. Without it, a third party could feed the app
an authorisation code of their choosing and the app would silently adopt whichever
account that code belongs to.

**AU10** — A failed authorisation MUST NOT be silent. The reason MUST be logged and
surfaced in the Sync panel. The original symptom — "it appears like it works, but then
says it's not connected" — was undiagnosable precisely because every failure path
returned quietly.

**AU5** — Tokens MUST be stored in IndexedDB, not `localStorage` or a cookie.
They MUST be treated as secrets: never logged, never included in an export, never
rendered in full in the UI.

**AU6** — The export format MUST NOT carry OAuth tokens. A backup file that grants
access to the user's Dropbox must not be the kind of thing that gets emailed
around. See 0011.

**AU7** — Sign-out MUST clear tokens and sync metadata. It MUST NOT delete local
entries, and the app MUST remain fully usable offline afterwards.

**AU8** — A user who declines or abandons authorisation MUST reach a working
local-only app, with sync simply off. There is no partial-setup state that breaks
tracking.

## Merge algorithm

This is the same union-and-resolve algorithm 0007 F-EXPORT-5 mandates for merging
a backup. Implementing it once, as a pure function in `domain/merge.ts`, serves
both paths.

**M1** — Merge MUST be a pure function: `(local, remote, now) → merged`. No I/O,
no clock reads. Fully testable, which matters more here than anywhere else in the
app.

**M2** — Merge MUST be a **union by `id`** across every entity type. Nothing that
exists on either side is dropped. The entity list is therefore the complete set of
stores in 0003: `projects`, `clients`, `tags`, `entries`, `contractPeriods`,
`nonWorkingDays`, `meta`. A new entity type MUST NOT be added to storage without
being added to the merge and the export envelope — otherwise it is the one thing
that never syncs, and it fails silently.

**M2.1** — Capacity entities MUST be merged by the same rules as everything else.
Non-working days and contracts reconcile exactly as entries do. Two devices marking
different days off MUST converge on the union of both.

**M2.2** — `deletedAt` on `NonWorkingDay` MUST be merged the same way as on entries
(M5), so a day removed on one device does not reappear from the other.

**M2.3** — `ContractPeriod` MUST be merged on `id` like any other record, but the
non-overlap invariant (0003 CT1) can be violated by a *union* of two valid
per-device sets: device A closes a period and device B extends the same one, and
the merge satisfies both locally and neither remotely. The merge MUST detect the
resulting overlap and MUST surface it for the user to resolve rather than silently
producing two open-ended periods.

**M2.4** — `label` and `partDay` are ordinary fields and merge by `updatedAt` with
no special handling. Free-text labels are not worth additional merge machinery.

**M3** — When the same `id` exists on both sides, the record with the later
`updatedAt` wins, field-for-field. Merge MUST NOT merge field by field, because
that can synthesise a record that never existed.

**M4** — On an exact `updatedAt` tie, the winner MUST be chosen by a deterministic
tiebreak (comparing the serialised records). This is essential: if two devices
picked differently on a tie, they would re-derive different results on every
subsequent sync and never converge.

**M5** — `deletedAt` is just another field, so a deletion wins or loses by
`updatedAt`. A device that deletes an entry while another edits it resolves to
whichever happened last. This is correct and needs no special case.

**M6** — Tombstones MUST be retained in the merged output. A device that has been
offline for a month must not resurrect entries deleted elsewhere.

**M7** — After merge, referential repair (0003 F1, F2) MUST run, so an entry
whose project lost a tie is repaired rather than dropped.

**M8** — `schemaVersion` MUST take the **maximum** of both sides, never be
downgraded by a stale device.

**M9** — If the remote `schemaVersion` is greater than the running build
supports, the device MUST refuse to sync, MUST NOT push, and MUST say so plainly
(0003 V4). It MUST NOT "helpfully" import what it cannot interpret. Syncing an
older client with a newer schema is how data gets corrupted.

**M10** — Settings in `meta` MUST merge by `updatedAt` like any other record.

**M11** — Merge output MUST be deterministic: identical inputs MUST produce
identical bytes. This is what makes it safe to retry a failed push.

### Clock skew

**CS1** — Last-write-wins depends on device clocks being roughly right. The known
failure mode is a device with a badly wrong clock winning merges it should have
lost.

**CS2** — The app MUST detect implausible `updatedAt` values — further into the
future than a small tolerance — and MUST surface them rather than silently
accepting them.

**CS3** — The app MUST NOT implement a logical clock or vector clock for this.
The complexity is not justified: time-tracking entries are append-mostly and
rarely edited concurrently. The realistic failure is a slightly-wrong attribution
of which edit was last, not data loss. This trade-off MUST be recorded rather
than hidden, because it is a real limitation.

**CS4** — `updatedAt` MUST be set from the local device clock at write time and
MUST NOT be taken from the remote, which would make the ordering circular.

## Sync cycle

**C1** — Triggered on: app open, a local write (debounced), manual "Sync now",
returning to the tab, and `pagehide`. The last of these matters because
`pagehide` is the last reliable lifecycle event before a tab is discarded, and is
more widely supported than `beforeunload` on mobile (0004 W7).

**C2** — Debounce MUST be long enough to coalesce a burst of edits — a
five-second pause is the intent — and MUST flush on a timer even if the user
keeps typing, so an extended session still syncs.

**C3** — A cycle MUST NOT overlap itself. A new cycle MUST wait for the current
one. Two concurrent cycles are the most likely source of duplicate or lost writes.

**C4** — Steps, in order:
1. `ensureAuth`. If it fails, abort silently and continue locally.
2. `pull` the remote blob.
3. If `null`, treat as first run: push local as-is.
4. If the remote `rev` matches the last rev we pushed, the remote is unchanged —
   push local.
5. Otherwise merge local with remote, write the merge result locally, then push.
6. Record `lastSyncAt` and the new `rev`.

**C5** — `push` MUST pass `expectedRev`. A provider-side rejection means
something else wrote the file since the pull, so the cycle MUST re-run from step
2 rather than retrying the same push. Retries MUST be bounded (three attempts) and
MUST back off. An unbounded retry loop against a conflict will spin.

**C6** — The app MUST NOT poll on a background interval. There is no server
inbound path, so a timer only produces empty cycles and keeps the device awake.
Syncing on open, on edit and on tab focus is sufficient and predictable.

**C7** — Only a *dirty* local database SHOULD trigger a push. The engine MUST NOT
push unchanged data on every open, which would cause needless conflicts on the
other device and needless API quota use.

**C8** — Sync status MUST be visible: last synced time, pending changes, error
state. A sync that silently fails is worse than no sync, because the user will
assume their other device is current.

**C9** — Conflicts MUST NOT be surfaced as a modal. Concurrent edits to time
entries are rare and LWW resolves them correctly; an interruption would be more
annoying than the problem. A log of what merged is enough.

## File location and identity

**FL1** — The remote path MUST be a fixed path inside the provider's app folder,
so one Dropbox account holds one time tracker's data.

**FL2** — The app MUST show the remote path and MUST provide "open the file in
Dropbox", so the user can recover the data manually if the app is ever lost. This
is a genuine escape hatch and the reason a single readable blob is worth keeping
even if a richer format were possible.

**FL3** — `meta` MUST record the provider id, the remote path and the last pushed
rev. Without the rev, C5's optimistic concurrency cannot work.

## Non-goals

- **Multiple accounts or shared databases.** One user, one file.
- **Real-time push.** No background sync service, no inbound webhooks (see C6).
- **Selective or partial sync.** The whole file, always.
- **Sync as a backup substitute** (SY5).
- **Cross-user or shared editing.** Explicitly a non-goal from 0001.

## Acceptance criteria

1. Two devices, both signed in, both can create entries while the other is
   offline; both converge to the union with no loss when both come online.
2. A merge performed twice on the same inputs yields identical output (M11).
3. Deleting an entry on device A does not resurrect it on device B (M6).
4. Pulling the app offline mid-sync corrupts nothing; local data stays usable and
   the next open recovers.
5. Declining authorisation leaves a fully functional local-only app (AU8).
6. An exported backup contains no OAuth tokens (AU6).
7. A remote `schemaVersion` newer than the build refuses to sync and does not
   push (M9).
8. Non-working days recorded on two devices while offline converge to the union
   (M2.1).
9. A non-working day deleted on one device does not reappear from the other
   (M2.2).
10. A merge that would produce overlapping contract periods is surfaced for the
    user to resolve, not silently accepted (M2.3).
